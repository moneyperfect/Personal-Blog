我用 Claude Code 写代码已经有一段时间了。它很强，但默认行为和我的习惯有不少冲突——比如它喜欢"顺手优化"我没让它动的代码，喜欢给我解释原理而不是告诉我怎么验证，喜欢用纯白背景配蓝色按钮做 UI。

于是我写了一份 `CLAUDE.md`，放在项目根目录。Claude Code 每次启动时会自动读取这个文件，按照里面的规则和我协作。

下面是这份协议的 5 条核心规则，以及每条规则背后解决的实际问题。

## 1. 思考先行

**规则：** 执行前必须显性化假设。如果有多种理解，把选项和权衡列出来让我选，不要默默替我做决定。

**解决的问题：** Claude Code 经常在理解不完整的情况下直接动手。比如我说"加个登录功能"，它可能自己决定用微信登录、邮箱登录还是手机号登录，然后直接写完。等我发现方向错了，已经浪费了一轮对话。

**实际效果：** 现在它遇到模糊需求会先停下来问我。比如"你要的是 Supabase Auth 还是自定义 HMAC 会话？"——这个问题问出来，比它自己猜对的概率高得多。

## 2. 极简主义

**规则：** 只提供解决当前问题的最少代码。不允许添加我没要求的"额外功能"、"灵活性"或"未来扩展性配置"。

**解决的问题：** AI 写代码有一种"过度工程化"的倾向。你让它加一个按钮，它可能顺手加了错误处理、loading 状态、无障碍属性、国际化支持——这些你可能根本不需要，但代码量翻了三倍。

**实际效果：** 50 行能解决的问题，它现在不会写 200 行。代码量少了，出 bug 的概率也低了，review 也更快。

## 3. 外科手术式修改

**规则：** 修改现有文件时，不要"顺手优化"相邻的代码、注释或格式。没坏的逻辑坚决不重构。

**解决的问题：** 这是我和 Claude Code 最大的冲突点。我让它改一个函数，它会"顺手"把整个文件的代码风格统一、把旧注释更新、把不用的 import 删掉。结果 diff 里 80% 是我不关心的格式变更，真正有用的改动淹没在噪音里。

**实际效果：** 现在它的改动非常精准。改 A 就是改 A，不会碰 B 和 C。git diff 干净了很多，review 效率提高了不少。

## 4. 目标与验证驱动

**规则：** 不要向我解释代码原理，直接告诉我如何从最终用户的视角去走通这个业务流。遇到复杂任务，先列执行计划，每一步附带验证方式。

**解决的问题：** 我是 Vibe Coder——我不看底层代码，我只看最终效果。Claude Code 默认喜欢解释"这个函数的作用是..."、"这里用了 XX 设计模式..."。这些对我来说没用，我需要知道的是"打开浏览器，点这个按钮，应该看到这个结果"。

**实际效果：** 现在它给我执行计划是这样的：

```
1. 创建登录 API → 验证: curl 调用返回 200 + set-cookie
2. 前端对接 → 验证: 浏览器登录后跳转到 dashboard
3. 权限校验 → 验证: 未登录访问 /admin 返回 401
```

每一步我都能在终端或浏览器里验证，不需要读代码。

## 5. 前端设计品味

**规则：** 禁用纯白和纯黑。背景用温暖的米色，标题用衬线字体，强调色用赤陶色或大地色。大圆角，宽 padding，呼吸感。图标用 Lucide，不用 Emoji。

**解决的问题：** AI 生成的 UI 默认是"程序员审美"——纯白背景、蓝色主色、直角边框、紧凑布局。能用，但不好看。而且每次生成的风格都不一样，同一个项目里可能出现三种不同的配色。

**实际效果：** 我把 Claude/Anthropic 官网的设计语言写进了规则里。现在所有新页面默认都是米色背景、衬线标题、黑色胶囊按钮。风格统一了，不用每次都手动调。

## 这份协议的本质

这 5 条规则不是技术规范，是协作协议。它定义的不是"代码怎么写"，而是"我和 AI 怎么配合"。

核心思路是：**AI 应该是我的执行层，不是决策层。** 它负责把我想清楚的事情高效实现出来，但不应该替我做选择。

`CLAUDE.md` 是 Claude Code 的原生功能——放在项目根目录，每次启动自动读取。不需要额外配置。

如果你也在用 Claude Code 或类似的 AI 编码工具，建议写一份自己的协作协议。不需要和我的一样，关键是把你的工作习惯明确化，减少和 AI 的摩擦。

我的完整 `CLAUDE.md` 如下：

```markdown
# 核心协作协议 (Vibe Coder 专属准则)

## 1. 思考先行 (Think Before Coding)
- 拒绝盲目假设：执行前必须显性化你的假设。如果对商业意图或产品逻辑有多种理解，
  必须把选项和 Tradeoffs 列出来让我选，绝对不要默默替我做决定。
- 蓝图确认：对于新需求，先输出架构蓝图。遇到模糊地带，立刻停止并向我提问。

## 2. 极简主义 (Simplicity First)
- 最小可用交付：只提供解决当前问题的最少代码。不允许添加我没要求的额外功能。
- 拒绝过度设计：不为一次性使用的代码创建抽象。50 行能解决，绝不写 200 行。

## 3. 外科手术式修改 (Surgical Changes)
- 精准打击：修改现有文件时，不要"顺手优化"相邻的代码。
- 清理残留：只清理由于本次修改而产生的冗余。

## 4. 目标与验证驱动 (Goal-Driven Execution)
- 黑盒验证优先：不要向我解释代码原理，直接告诉我怎么从用户视角验证。
- 多步任务拆解：每步附带验证方式（终端日志或浏览器变化）。

## 5. 全局前端设计品味 (Claude UI Aesthetic)
- 色彩：禁用纯白纯白。背景用米色/纸张色，正文用深炭灰。
- 强调色：柔和的赤陶色、暖橙色或大地色。
- 排版：标题用衬线字体，正文用无衬线字体。
- 组件：大圆角、宽 padding、呼吸感。不用生硬边框。
- 图标：Lucide Icons，禁止 Emoji。
```
